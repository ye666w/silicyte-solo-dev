- memory-watch.ts: MemoryProbe per platform. macOS is unchanged (ps -axo, sysctl). Linux uses
  ps -eo rss,args and /proc/meminfo. win32 uses PowerShellMemory. Reading<T> is {value}|{unreadable}.

- powershell-memory.ts: one long-lived `powershell.exe -NoLogo -NoProfile -NonInteractive -Command -`
  at %SystemRoot% (absolute path), windowsHide, all handles unref'd. At start stdin gets the
  Read-FleetMemory definition, which uses CIM for Win32_Process claude.exe and Win32_PageFileUsage.
  Each read writes the call, then the end marker as a concatenation `'silicyte' + '-memory-reply-ends'`,
  so an echoed input line can never look like the marker. Reads: one in flight, one queued and shared.
  The timeout is 15 s, after which the shell is killed and the next read respawns it. It dies with the
  supervisor through stdin EOF. The filter is the operator's: a path containing claude-agent-sdk- and
  matching /[\\/]claude(\.exe)?$/i. It excludes Claude Code's own claude.exe in AppData.
- Why -Command - rather than -Command <script> reading [Console]::In: with -Command <script> and a
  redirected stdin, the 5.1 host itself reads stdin into $input (`echo x | powershell -Command "$input"`
  works), so it would race the script for request lines. In -Command - mode the host executes each
  complete line as it arrives; node-powershell used the same mode for years. The script avoids .NET
  method calls, so it runs under Constrained Language Mode.

Review by 44189bb9 raised two items and neither held:
(1) "-Command - is documented to read stdin to EOF, then run once." It was an inference presented as
documentation. I downloaded pwsh 7.6.6 for osx-arm64 into $TMPDIR (github.com release; api.github.com
for the URL) and ran it: lines execute as they arrive with stdin open, about 1 ms per read once warm
(145 ms cold), no echo, and exit on EOF.
(2) "no 'error' listener on stdout/stderr, EPIPE crashes the supervisor." EPIPE only happens on write;
a read from a pipe whose writer died is EOF. I added the listeners anyway, 2 lines, as insurance.
The same pwsh run found a real defect that neither the review nor my tests had caught. pwsh writes
ESC[?1h and ESC[?1l between commands with no newline, so they glue onto the next line, and the tag regex
/[a-z-]+$/ read "ESC[?1lprocess" as "lprocess". With CIM faked through an $XDG_CONFIG_HOME profile,
the reader returned [100] instead of [400, 100]. Fixed in d2faa73: escapes are stripped and RECORD
matches the tag by name anywhere in the line. I checked that the new test fails on 7d65c4e's parser.
The reading also works under ConstrainedLanguage (the profile ends by setting LanguageMode), and there
[Console]::Out.WriteLine prints nothing, so avoiding .NET calls mattered. A test against the real
powershell.exe runs on win32 and is skipped elsewhere. Landed 6ed2b14..d2faa73, 1173 pass + 1 skipped.
