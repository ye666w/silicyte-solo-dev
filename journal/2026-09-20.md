## A lesson about my own task-writing, not about the worker

I sent `worker-a36f9e40` to map which assertions break, and wrote "read the tests, do not run
them; nothing is implemented yet so they all pass." Its answer to that part was **wrong** — it
reported that nothing breaks, reasoning that the old and new guards agree "when both are set by
the normal flow", which is true and misses the only case that matters, the one where `Resume`
clears one and not the other. I had already measured a red test by then.

The worker's own skill tells it to run things. My task overrode that. **When the question is what
breaks, the answer comes from running, and a task that forbids running has answered a different
question.** If a change is not implemented yet, the useful instruction is to implement the
smallest version and run, or to say plainly that the answer is a prediction.

What it did get, and what paid for the whole round, was one line: **no test anywhere uses
`status: 'rejected'`** — the `reading()` helper hardcodes `'allowed'`, so every test of the limit
machinery was a test of the percentage comparison and the entire account-refused path was
untested. That is a fact, checkable in seconds, and it is why the gap survived. Its list of
missing tests also overlapped three of the four I had derived independently, which is a decent
cross-check on both of us.

Shape of the round: large input, small answer, and the small answer was worth it. The part that
went wrong went wrong in my prompt.

## What I am actually here for, and the finding it led to

The operator corrected the premise: this fleet is not here to work a board. It is here so the two
of us make the architecture not rubbish, and `workspace/RESEARCH.md` is where that work is kept.
Its soft spot #5 is one I wrote myself and labelled "the highest-yield audit available here and
has not been done" — ~25 private fields of per-session coordination state in `supervisor.ts`,
each a Set or Map keyed by sid, each added in one place and removed by hand somewhere else.

It has stopped being a hypothesis. Three confirmed instances of the same shape, all in that file:
`af2b817` (the set filled after an await), `1f9dbac` (the same set empty in two situations), and
`compactionRequested` (deleted on one event only, stuck forever after a cancelled compaction).

**Verified by reading the two methods, not inferred.** Seventeen of those collections are keyed by
sid. `closeOne()` :509 — the one place a session ends for good — erases **five** of them:
`humanOutbox`, `reportsHeldUntilUnfreeze`, `clearWhenTheTurnEnds`, `spentBeforeTheCurrentProcess`,
`toldTheOperatorItReadsLow`. `clear()` :1050 erases **one**: `clearWhenTheTurnEnds`. And `clear()`
is the sharper case, because the sid survives while the conversation is thrown away, so every
entry still keyed by it is now about a conversation that does not exist.

So the defect is not any one field. **There is no single place that says "this sid is finished,
forget it."** The registry owns the lifecycle; seventeen side-tables each have to remember on
their own. That is a defect generator, and adding an eighteenth field is how the next one arrives.

Three workers are sweeping all seventeen — add sites, erase sites, which lifecycle moments reach
an erase, and what breaks when the erase never fires. Whether "eleven are never cleaned on close"
holds is theirs to settle; what is above is what I checked myself.

## Two findings verified myself, before the audit is finished

**Landed work never reaches a new session.** Sessions land by `git push origin HEAD:main`, which
moves the remote. Worktrees are cut by `Worktrees.create` from the product checkout's **local**
`main`, which that push does not move. No session may move it either — the write guard refuses
any git subcommand that would write a checkout the fleet reads from, and it is right to. Nothing
in the product does it. So the local `main` advances only when a human runs git in that
directory. Measured, not reasoned: `origin/main` at `b6f961a`, all six worker worktrees at
`af2b817`, and three of six audit reports were consequently written against code one commit stale.
The guard's own refusal text says a change "reaches it from a worktree of its own" — true for the
remote, and it leaves the local checkout behind forever.

**`clear()` throws the conversation away and keeps every judgement formed about it.** This is the
sharp version of soft spot #5, and it is not what I first hypothesised. Cleanup is not organised
by lifecycle event at all; it is organised by *process exit*. `clear()` routes through
`detachFromItsProcess` :952, so everything process-scoped is cleaned — `idleSince`,
`backgroundTasksBySid`, the handle. Everything conversation-scoped survives, because nothing in
the code distinguishes the two:

    compactionRequested        a cancelled compaction disables it for the new conversation too
    refusalsBySid              old refusal timestamps count toward the new conversation's streak
    toldTheOperatorItReadsLow  the drain ends with comesBack=true, so :401 never fires
    humanOutbox                a queued human message is delivered into a conversation that
                               has no idea what it refers to
    reportsHeldUntilUnfreeze   same

So the missing idea is not "a cleanup function". It is that **process identity and conversation
identity are the same `sid`**, and the code has no way to say which of the two a piece of state
belongs to. Add a field and you are silently choosing one by accident.

**The cost of an edit, measured.** `supervisor.ts`: 47 private fields, 112 methods, one class.
`registry` is touched by 62 of those methods, `bus` by 29. Eighteen methods touch four or more
distinct fields; `nudgeIfEverythingIsQuiet` touches eleven. There is no module boundary, so the
only honest way to change anything is to read the file. That is the token bill on every edit, and
it is also why the criticals cluster here rather than anywhere else.
