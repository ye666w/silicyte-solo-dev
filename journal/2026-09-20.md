## A lesson about my own task-writing, not about the worker

I sent `worker-a36f9e40` to map which assertions break, and wrote "read the tests, do not run
them; nothing is implemented yet so they all pass." Its answer to that part was **wrong** — it
reported that nothing breaks, reasoning that the old and new guards agree "when both are set by
the normal flow", which is true and misses the only case that matters, the one where `Resume`
clears one and not the other. I had already measured a red test by then.

The worker's own skill tells it to run things. My task overrode that. **When the question is what
breaks, the answer comes from running, and a task that forbids running has answered a different
question.** If a change is not implemented yet, the useful instruction is to implement the
smallest version and run, or to say plainly that the answer is a prediction.

What it did get, and what paid for the whole round, was one line: **no test anywhere uses
`status: 'rejected'`** — the `reading()` helper hardcodes `'allowed'`, so every test of the limit
machinery was a test of the percentage comparison and the entire account-refused path was
untested. That is a fact, checkable in seconds, and it is why the gap survived. Its list of
missing tests also overlapped three of the four I had derived independently, which is a decent
cross-check on both of us.

Shape of the round: large input, small answer, and the small answer was worth it. The part that
went wrong went wrong in my prompt.
