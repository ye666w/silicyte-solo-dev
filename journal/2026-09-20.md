## Two findings verified myself, before the audit is finished

**Landed work never reaches a new session.** Sessions land by `git push origin HEAD:main`, which
moves the remote. Worktrees are cut by `Worktrees.create` from the product checkout's **local**
`main`, which that push does not move. No session may move it either — the write guard refuses
any git subcommand that would write a checkout the fleet reads from, and it is right to. Nothing
in the product does it. So the local `main` advances only when a human runs git in that
directory. Measured, not reasoned: `origin/main` at `b6f961a`, all six worker worktrees at
`af2b817`, and three of six audit reports were consequently written against code one commit stale.
The guard's own refusal text says a change "reaches it from a worktree of its own" — true for the
remote, and it leaves the local checkout behind forever.

**`clear()` throws the conversation away and keeps every judgement formed about it.** This is the
sharp version of soft spot #5, and it is not what I first hypothesised. Cleanup is not organised
by lifecycle event at all; it is organised by *process exit*. `clear()` routes through
`detachFromItsProcess` :952, so everything process-scoped is cleaned — `idleSince`,
`backgroundTasksBySid`, the handle. Everything conversation-scoped survives, because nothing in
the code distinguishes the two:

    compactionRequested        a cancelled compaction disables it for the new conversation too
    refusalsBySid              old refusal timestamps count toward the new conversation's streak
    toldTheOperatorItReadsLow  the drain ends with comesBack=true, so :401 never fires
    humanOutbox                a queued human message is delivered into a conversation that
                               has no idea what it refers to
    reportsHeldUntilUnfreeze   same

So the missing idea is not "a cleanup function". It is that **process identity and conversation
identity are the same `sid`**, and the code has no way to say which of the two a piece of state
belongs to. Add a field and you are silently choosing one by accident.

**The cost of an edit, measured.** `supervisor.ts`: 47 private fields, 112 methods, one class.
`registry` is touched by 62 of those methods, `bus` by 29. Eighteen methods touch four or more
distinct fields; `nudgeIfEverythingIsQuiet` touches eleven. There is no module boundary, so the
only honest way to change anything is to read the file. That is the token bill on every edit, and
it is also why the criticals cluster here rather than anywhere else.

## Durability and the panel, both verified by hand after the reports

**`registry.json` is the only critical state file written non-atomically.** `spending.ts:112` and
`operator-questions.ts:194` both write a half-written temp file and `renameSync` it into place.
`registry.ts` calls `writeFileSync` straight at the destination. So the pattern exists in this
codebase, was applied twice, and was not applied to the file whose loss costs the most: a write
interrupted mid-flight leaves truncated JSON, `loadPersisted()` :140 swallows the parse error and
returns `[]`, and the fleet comes up believing no session ever existed. Silent, total, and a
one-line fix by copying code already in the repo. `timings.json`, `connectors.json` and
`integrations.json` are also non-atomic but all three are cheap to recreate.

**The panel's escaping is sound, and that is a finding worth recording as a negative.**
`renderMarkdown` :793 calls `escapeHtml` **first** and applies the markdown substitutions to the
already-escaped string, which is the correct order — the dangerous version does it the other way
round. Eleven `innerHTML` sites, every one either escaped or fed a string built from escaped
parts. So despite being 2683 lines, `app.html` is not where the risk is, and it does not belong
near the front of any rebuild plan. Its real problem is different and smaller: `renderGraph` is
called on every state event with no debounce and rebuilds the whole SVG, which is invisible at
nine sessions and would not be at a hundred.

One worker claimed the file cannot be split without a build step "because no modules are
available". That is wrong — `<script type="module" src="./x.js">` needs no build step, and the
page uses a single plain `<script>` today purely by choice. The constraint is no *build*, not no
*modules*. Worth remembering before anyone repeats the claim.

## Compaction: cause found, and two of my own claims retracted

Level 1 of the plan ("establish why the CLI cancels a compaction") is answered and fixed. It
is not length, and the mechanism was never dead.

Measured against worker-f6444092 held near 30% context. Three rounds, each attributable
because no human typed anywhere near it:

    /compact                                 8 chars    fired
    /compact <57-character single line>     66 chars    fired
    /compact <3.5 KB, single line>        3.5k chars    fired
    /compact <3.7 KB, paragraph breaks>   3.7k chars    cancelled

A slash command ends at the first newline. Everything after it stops being part of the
command, and the compaction is cancelled in silence. Landed as 38579d9: whitespace is
collapsed, so a long instruction arrives whole and on one line. Deliberately not a length cap
— the test asserts the fortieth line survives, so nobody later "repairs" this by truncating.

Two things I had written down were wrong, both in the alarming direction:

  - "No compacted event in either fleet's log, so the product's cost model rests on a
    mechanism nobody has observed run." The threshold path calls queueCompaction with no
    instructions — exactly the case that always fires. Nothing had ever reached 75%. Zero
    events meant zero sessions at the threshold, not a dead mechanism.
  - "The 0-char report is the signature of a cancellation." It follows a successful compaction
    too. The only discriminator is the `compact` line in .silicyte/activity.log.

The method is the reusable part. My own two data points were worthless: the operator typed
/compact 25 seconds after my own attempt and exactly one compaction fired, so neither could be
attributed. A worker is an isolated subject with nobody else typing into it, and three clean
rounds cost one Haiku session. When a measurement about my own behaviour is confounded by the
operator sharing the channel, move the experiment to a worker.

## 2.1: the slice that turned out not to exist (fa5b0fe)

47163f0 ended by naming humanOutbox and reportsHeldUntilUnfreeze as the next slice,
"deliveries meant for a conversation that clear() can throw away". I checked before moving
them, and the reasoning was wrong. clear() cannot throw either away:

  - An outbox message is queued only while a session is busy or starting, and clear() refuses
    a busy session outright. If the turn ends before the outbox drains, a second refusal
    counts what the session has not read.
  - Held reports exist only for a frozen reader. clear() refuses a frozen session outright,
    and the only transition out of frozen delivers them first — markWaiting and markWorking
    both decline to touch a frozen session, so there is no other way out.
  - closeOne drops both, each with an event.

So: no code change. What was actually missing is that this rests on three separate refusals
agreeing, and nothing tested the agreement. Two tests now pin it. Relaxing the frozen refusal
would strand reports in silence and no suite would have noticed.

Worth keeping as a habit: verify the defect still exists before fixing it, especially when the
claim is my own from an earlier commit. Second time today that a confident note of mine did not
survive being checked — the first was the compaction diagnosis. Both were written at the end of
a long stretch, which is probably the pattern rather than a coincidence.

reassigned in five places — `this.frozenByTheLimit = new Set()` — and SessionState keeps a

halt or limit release) the mechanism emptied one Set while the supervisor filled another.

Why nothing caught it, which is the part worth remembering:

  - Every reader filters by registry status, and a closed session is never 'frozen', so the
    stale sids were ignored rather than acted on. It leaked, it did not misbehave.
  - The guard test checks that collections are *declared* through SessionState. This one was.
  - whatIsStillHeldAbout cannot see it either, and is worse than useless here: it inspects the
    collection SessionState was given, which after a swap is the empty one, so it answers
    "not held" — wrong in the reassuring direction. A query built to detect leaks is blind to
    the one way the mechanism itself can be detached.

Fixed by making it impossible rather than detectable: all thirteen declarations are readonly,
so the compiler refuses reassignment (verified: TS2540), and the five sites empty in place. A
test refuses a newly added non-readonly declaration, because the compiler has nothing to say
about a field nobody has reassigned yet. Both guards were checked by reintroducing the defect
and confirming each fails — a guard nobody has seen fail is decoration.

Lesson for the rest of 2.2: an abstraction that owns state by holding a reference is only as
strong as the field that points at it. Every future extraction must ask not just "is this
declared correctly" but "can the declaration be swapped".

## Step 4 done, and it exposed the real limit: ssh does not cross the sandbox

Root is inside the sandbox now. Filesystem behaves exactly as designed — the system prompt shows
the allow list and it matches what the code builds, including workspace/.git and the worktree.

Network does not, and the fix I landed for it was aimed at the wrong thing:

    git ls-remote (ssh)               Broken pipe          blocked
    curl https://github.com           http_code=200        allowed
    git ls-remote (https)             "could not read Username"   reached it, wanted credentials

So egress goes through an HTTP filtering proxy. allowedDomains governs HTTP(S) through that
proxy. Raw TCP to port 22 is not expressible in the settings at all — the network section offers
allowedDomains, httpProxyPort, socksProxyPort, unix sockets and mach lookups, and nothing that
says "let this host through on this port". Granting the ssh agent socket was necessary and not
sufficient: the agent was never the problem, the transport was.

That means a sandboxed session cannot push over ssh, full stop, and no amount of tuning the
allow list changes it. What is left is a choice about how landing works, which is the operator's:

  1. Root keeps mayRunOutsideTheSandbox. Everything works, and the session with the most
     authority is the one thing not contained. Defeats most of the point.
  2. Remotes move to HTTPS with a credential the sandbox can read. Smallest change, keeps every
     role contained, and the proxy already passes github.com. Costs: a token on disk or in a
     keychain the sandbox can reach, usable by any session that can push — which is the same
     set that can push today, so the scope is bounded but not nothing. gh is installed and not
     logged in; the repo's helper is osxkeychain and it supplied nothing.
  3. Landing moves into the supervisor, which is not sandboxed — it already runs git pull for
     the rails there. Then no agent needs network at all and the sandbox can be its tightest.
     Architecturally the best answer and the most work, and it cannot be built from inside the
     sandbox because building it requires landing it.

Recommending 1 then 3: restore the flag so landing works, build landing-through-the-supervisor,
then drop the flag for good. 2 is the cheap answer if the token is acceptable.

## Landing moved to the supervisor, and the operator's objection is why it is shaped this way

Trello #56. The note on the card was: are you sure landing belongs in the supervisor, it will
hurt if there is a conflict. That objection is what made the design right rather than merely
possible.

Landing is three operations and only two of them touch the network, and those two are the two
with no judgement in them. **Fetching** is the supervisor's, done once in the shared checkout —
every worktree of that repository sees the result, because worktrees share one object store and
one set of refs. **Rebasing, and whatever conflict it turns up**, stays in the session, local,
exactly as before. **Pushing** is the supervisor's.

What makes it more than a rearrangement is the refusal. The supervisor will not push a branch
that does not already contain the remote main, so a conflict cannot become its problem even by
accident: it comes back with the reason, and the only way through is a rebase in the worktree that
knows what the code means. The refusal doubles as the fetch, so a session with no network can
still get current: call it, be told to rebase, rebase against the ref the call just refreshed,
call again.

`fleet_land` takes no session id. It lands the branch of whoever called it, so there is no
argument through which one session could put its work on main under another name.

**The half that nearly got forgotten.** The tool knew only the repositories in the config, and the
journal and the map live in a repository of their own that is not one of them. Closing the sandbox
with that half missing would have left every session able to ship code and unable to write down
what it learned doing it — and this file is the only thing here that outlives a conversation by
design. `repo: 'journal'` lands that one.

This entry is the proof: it was written, committed, and pushed through the supervisor with no
session touching the network.

**And the rails check earned its keep.** The first restart onto this was refused, naming a test of
mine that had passed ten times out of ten locally and failed in the fork checkout. Not the code —
the test waited for a scheduler turn where it needed a state, and the rails run the suite on a
machine that is busy running the fleet. Ten green local runs said nothing. The only thing that
caught it was the check that refuses to restart onto code the suite does not pass where it will
actually run.
